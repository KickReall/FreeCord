# FreeCord

**Self-hosted мессенджер с микросервисной архитектурой.** Аналог Discord, который вы разворачиваете на собственном сервере и полностью контролируете: без облаков, без телеметрии, без внешних зависимостей.

Серверная часть — четыре независимых микросервиса на C++. Клиент — кроссплатформенное десктопное приложение на C# / Avalonia. Общаются по собственному бинарному протоколу поверх TCP.

---

## Возможности

- **Регистрация и вход** — пароли хешируются PBKDF2-HMAC-SHA256 (100 000 итераций), в открытом виде не хранятся
- **Комнаты** — создание, переключение, системная комната с уведомлениями
- **Обмен сообщениями в реальном времени** — сообщение доставляется всем, кто открыл комнату, мгновенно
- **История переписки** — сохраняется в SQLite, переживает перезапуск сервера
- **Уведомления** — о создании комнат и регистрации новых пользователей, рассылаются всем клиентам
- **Keepalive** — ping/pong с таймаутом, мёртвые соединения закрываются автоматически

## Архитектура

```
                        ┌──────────────┐
        TCP :6000       │              │
   Клиент ──────────────▶   Gateway    │   сессии, маршрутизация, fanout
                        │              │
                        └──────┬───────┘
                               │ TCP (internal)
             ┌─────────────────┼─────────────────┐
             ▼                 ▼                 ▼
        ┌─────────┐       ┌─────────┐       ┌──────────┐
        │  Auth   │       │  Room   │       │ Message  │
        │  :6001  │       │  :6002  │       │  :6003   │
        └────┬────┘       └────┬────┘       └────┬─────┘
             │                 │                 │
             ▼                 ▼                 ▼
     freecord_auth.db   freecord_rooms.db  freecord_messages.db
```

Клиент знает только один адрес — **Gateway**. Всё остальное скрыто за ним.

### Роль каждого сервиса

| Сервис | Порт | Отвечает за |
|---|---|---|
| **Gateway** | 6000 | Единственная точка входа. Держит долгоживущие соединения с клиентами (поток на клиента), хранит сессии в памяти, проксирует запросы во внутренние сервисы и рассылает события. Собственной БД не имеет. |
| **Auth** | 6001 | Регистрация и проверка учётных данных. Хеширование паролей. |
| **Room** | 6002 | Комнаты: создание, список, системная комната. |
| **Message** | 6003 | Сохранение сообщений и выдача истории. |

Каждый сервис работает **только со своими таблицами** — изоляция данных соблюдается даже при использовании файловых БД на одном хосте.

### Ключевые решения

**Не P2P, а через сервер.** Клиент отправляет сообщение только на сервер; сервер сам определяет получателей и рассылает. Это позволяет вести историю, контролировать доступ и работать за NAT без пробивания соединений.

**Активная комната живёт в памяти, не в БД.** Переключение между комнатами — операция над сессией в оперативной памяти Gateway, а не запись в базу. Отправка сообщения не требует ни одного запроса к `room_service`.

**Денормализация имени автора.** Имя отправителя записывается в таблицу сообщений в момент отправки. Это избавляет от join-запросов между базами разных сервисов, а смена никнейма не переписывает историю задним числом — так же поступает Discord.

**Иерархия типов сообщений по диапазонам.** `0x0000–0x0FFF` — клиент ↔ gateway, `0x1000+` — внутренние вызовы между сервисами. Один парсер обслуживает оба слоя, но сообщения не смешиваются.

## Протокол

Собственный бинарный формат поверх TCP. Каждый кадр — фиксированный заголовок плюс полезная нагрузка:

```
┌────────────────┬──────────────┬──────────────┬─────────────┐
│ length (u32)   │ type (u16)   │ sequence(u32)│  payload    │
└────────────────┴──────────────┴──────────────┴─────────────┘
      4 байта        2 байта        4 байта      length байт
```

Строки кодируются как `uint16` длина в байтах + UTF-8 данные, без null-терминатора. Числа — little-endian, что делает представление идентичным на стороне C++ (`#pragma pack(1)`) и C# (`BinaryWriter`).

TCP передаёт **поток байт**, а не сообщения, поэтому чтение всегда идёт в цикле до набора нужного количества байт — иначе кадры разъезжаются по границам. Это учтено на обеих сторонах.

## Технологический стек

**Сервер**
- C++20, кроссплатформенный слой над Winsock2/BSD sockets (Windows и Linux)
- SQLite через SQLiteCpp
- OpenSSL (хеширование паролей)
- nlohmann-json (конфигурация)
- CMake + vcpkg

**Клиент**
- .NET 8+, C#
- Avalonia UI (кроссплатформенный XAML)
- CommunityToolkit.Mvvm
- `FreeCord.Protocol` — самостоятельная библиотека протокола, не зависящая от UI

## Сборка и запуск

Сервер собирается и запускается одинаково на Windows и Linux — по паре команд, без ручной настройки CMake:

```powershell
# Windows
.\build-windows.ps1
.\run-windows.ps1
```

```bash
# Linux (в т.ч. WSL2)
./build-linux.sh
./run-linux.sh
```

Клиент:

```bash
cd client/FreeCord.Desktop
dotnet run
```

Полная инструкция с требованиями, установкой vcpkg с нуля и разбором типичных ошибок — в [BUILDING.md](BUILDING.md) (на русском и английском).

## Планы

- [x] **Портирование сервера на Linux** — слой абстракции над сокетами, собирается и работает на Windows и Linux
- [x] **JSON-конфигурация** — порты, пути к БД и адреса вместо констант в коде
- [ ] **Система миграций БД** — сейчас таблицы создаются через `CREATE TABLE IF NOT EXISTS` при старте сервиса, а изменение схемы требует удаления файла базы. Планируется таблица `schema_version` и последовательное применение SQL-файлов, чтобы схему можно было менять на работающем сервере без потери данных
- [ ] **TLS** — шифрование соединений (обязательное для клиента, опциональное между сервисами), самоподписанный сертификат с проверкой по отпечатку
- [ ] **Установщик для сервера** — скрипт развёртывания, systemd-юниты, автозапуск
- [ ] **Ролевая модель** — приватные комнаты, права доступа
- [ ] **Голос и видео** — UDP-транспорт, SFU-релей на сервере, Opus и H.264 через FFmpeg
- [ ] **Доработка интерфейса** — список участников, аватары, группировка сообщений

## О разработке

Проект разрабатывается пошагово, с проверкой каждого этапа перед переходом к следующему: сначала сетевой слой, затем сервисы по одному, затем клиент. Такой порядок позволяет локализовать ошибку в только что написанном коде, а не искать её сразу в нескольких новых компонентах.

**Весь код в этом репозитории написан при участии Claude (Anthropic).** Архитектурные решения — от выбора модели SFU вместо P2P до способа хранения активной комнаты — обсуждались и принимались совместно; Claude предлагал варианты с разбором компромиссов, а реализация и проверка выполнялись автором репозитория.
