# FreeCord

Self-hosted мессенджер (аналог Discord). Сервер — микросервисы на C++, клиент — C# / Avalonia. Собственный бинарный протокол поверх TCP. Никаких внешних зависимостей и облаков: всё разворачивается на своём хосте.

Общение с пользователем — на русском языке.

---

## Команды

Автосборка для разработки (дев-скрипты в `server/` — не для установщика, только чтобы быстро собрать и перезапустить). Каждый сам находит корень `server/`, ставит зависимости через vcpkg, конфигурирует и собирает, останавливает уже запущенные сервисы и всегда чистит `*.db` после сборки — так что перенос папки проекта на другую машину/путь ничего не ломает. Запускать из корня репозитория:
```powershell
.\server\build-windows.ps1
```
```bash
./server/build-linux.sh   # внутри WSL/Linux; путь проекта должен быть в родной ФС (не /mnt/*)
```

Автозапуск всех четырёх сервисов разом — вывод всех процессов идёт в одну консоль, каждый сервис своим цветом (сами сервисы уже пишут строки с префиксом `[имя]`, скрипт просто красит). `Ctrl+C` останавливает всё:
```powershell
.\server\run-windows.ps1
```
```bash
./server/run-linux.sh
```

Ручная сборка под Windows (из папки `server/`), если скрипт почему-то не подходит:
```powershell
cd server
mkdir build-windows; cd build-windows
cmake .. -DCMAKE_TOOLCHAIN_FILE=C:/vcpkg/scripts/buildsystems/vcpkg.cmake
cmake --build .
```

Сборка под Linux делается отдельно, в WSL/Linux-окружении, в свою папку `build-linux` — см. раздел «Портирование на Linux» ниже.

Запуск — четыре процесса, каждый в своём окне, из папки `server/build-windows`:
```
.\services\auth\Debug\auth_service.exe
.\services\room\Debug\room_service.exe
.\services\message\Debug\message_service.exe
.\services\gateway\Debug\gateway_service.exe
```

Клиент:
```powershell
cd client\FreeCord.Desktop
dotnet run
```

Зависимости через vcpkg: `sqlite3`, `sqlitecpp`, `openssl`, `nlohmann-json`.

Все четыре сервиса при старте читают `config.json` и папку `db/` (миграции + SQL-запросы) из своей рабочей директории. CMake копирует их из `server/` в `server/build-windows/`/`server/build-linux/` при каждой сборке (таргет `copy_config`) — именно туда, откуда по инструкции выше и запускаются `.exe`. Файла нет, он битый, или не хватает SQL-файла — сервис сразу падает с понятным сообщением об ошибке, никаких скрытых дефолтов в коде нет.

**Что вынесено из кода, а что нет.** Порты, пути к БД, адрес хоста для внутренних вызовов, таймауты (`gateway.recvTimeoutMs`, `gateway.clientIdleTimeoutSec`, `gateway.serviceCallTimeoutMs`), лимит длины сообщения (`message.maxTextLength`), пути к TLS-сертификату и ключу (`gateway.tls.certPath`, `gateway.tls.keyPath`) — в `server/config.json`. Все SQL-запросы и схемы таблиц — в `server/db/<сервис>/`. В коде остаётся только то, что связано с шифрованием (параметры PBKDF2 в `PasswordHasher.cpp`) и внутренние инварианты, завязанные на другие части системы: `SYSTEM_ROOM_ID` (совпадает с seed-данными в `server/db/room/migrations/001_initial.sql`) и `kMaxPayloadSize` в `TcpFramer.cpp` (должен совпадать с тем же лимитом в C#-клиенте — иначе сервер и клиент по-разному решат, что «слишком большой» кадр).

## Критические инварианты

**Сериализация C++ и C# должна совпадать байт в байт.** При изменении любой структуры в `server/common/include/*Messages.h` обязательно нужна зеркальная правка в `client/FreeCord.Protocol/Payloads.cs`, и наоборот. Порядок полей, их типы и размеры должны совпадать точно. Формат: строки — `uint16` длина в байтах + UTF-8 без null-терминатора; числа — little-endian (совпадает у `#pragma pack(1)` в C++ и `BinaryWriter` в .NET). При добавлении нового `MessageType` его нужно продублировать в `client/FreeCord.Protocol/MessageType.cs` с тем же числовым значением. То же самое для битов `Permission` — `server/common/include/Permissions.h` и `client/FreeCord.Protocol/Permissions.cs` обязаны совпадать значение в значение.

**Схема БД версионируется через `PRAGMA user_version`, миграции — файлы, не удалять руками.** Каждый репозиторий при старте вызывает `ApplyMigrations(db, LoadMigrationsFromDirectory("db/<сервис>/migrations"))` — путь относительно рабочей директории процесса (`server/db/` в исходниках, копируется в `server/build-*/db/`) — накатывает по порядку файлы `NNN_описание.sql` с номером больше текущей версии, каждый в своей транзакции. Новая версия схемы = новый файл `002_....sql` рядом с `001_initial.sql`, **не редактировать уже применённые файлы** — раннер не увидит изменений в файле с уже накаченным номером. `.db`-файл теперь никогда не нужно удалять вручную.

**Новый сервис слушает порт через `CreateListenSocket(port)` (`PlatformSocket.h`), не через голые `socket()`/`bind()`/`listen()`.** Кроме кадрирования, эта функция включает `SO_REUSEADDR` — без него быстрый перезапуск сразу после остановки (обычное дело при разработке, и при `systemd restart` в проде) утыкается в `TIME_WAIT` и `bind()` падает почти на минуту. Все четыре сервиса проверяют её результат на `kInvalidSocket` и падают с понятным сообщением, а не продолжают тихо жить, ничего не слушая.

**`auth_service` многопоточный, как остальные три, а не исторический особый случай.** Он самый нагруженный из внутренних сервисов (логин с намеренно медленным PBKDF2, `IsIpBannedRequest` на каждое новое подключение к gateway), поэтому `UserRepository` держит свой `m_mutex` (как `RoomRepository`) — если добавляешь туда новый метод, оборачивай тело в `std::lock_guard`, не полагайся на то, что вызовы редкие.

**Чтение из сокета всегда в цикле.** TCP отдаёт поток байт, а не сообщения; один `recv` может вернуть меньше запрошенного. Это уже реализовано в `RecvAll`/`SendAll` в `TcpFramer.cpp` и в `ReadExactlyAsync` на стороне C#. Не заменяй на одиночные вызовы.

**Порядок функций в gateway/main.cpp.** `SendToSession` → `BroadcastToRoom` / `BroadcastToAll` → `Handle*` → `ClientThread` → `main`. C++ читает файл сверху вниз, вызов выше определения не компилируется.

**Запись в чужой сокет только через `SendToSession`.** Fanout идёт из потока одного клиента в сокеты других. Каждая сессия имеет свой `sendMutex`; прямой `SendFrame` в чужой сокет приведёт к перемешиванию кадров.

**Сертификат гейтвея не должен меняться между перезапусками без предупреждения.** Клиент закрепляет его отпечаток при первом подключении (TOFU, `client/FreeCord.Protocol/TrustedServerStore.cs`) и при следующих сверяет — расхождение обрывает соединение с явной ошибкой, а не молча переподключается. `TlsContext` поэтому генерирует `gateway.crt`/`gateway.key` только если файлов ещё нет, и переиспользует их при каждом следующем старте. Если сертификат всё же пришлось перевыпустить (например, файлы удалили руками), все клиенты, уже закрепившие старый отпечаток, откажутся подключаться — это ожидаемо, а не баг.

**Не передавать OpenSSL свой `FILE*`.** На Windows со сборкой из vcpkg (динамический OpenSSL) вызов вроде `PEM_write_PrivateKey(fopen(...), ...)` падает с `OPENSSL_Uplink ... no OPENSSL_Applink` — `FILE*` не переживает переход через границу DLL со своим CRT. `TlsContext::GenerateSelfSignedCertificate` поэтому пишет PEM в память через `BIO_s_mem()` и сохраняет на диск сам через `std::ofstream`, а не отдаёт файловый дескриптор напрямую в OpenSSL.

**SIGPIPE игнорируется на Linux с самого старта (`SocketLibraryGuard`, единственный сокетный RAII-объект, который есть у всех четырёх сервисов).** Без этого запись в сокет, который уже закрыт с другого конца — в том числе намеренно, самим же сервером через `ShutdownSocket` (см. бан по IP выше) — убивает весь процесс сигналом по умолчанию, без единой строчки в лог: gateway_service именно так и падал при бане собственного IP, пока это не обнаружилось на WSL (на Windows такого сигнала нет, `send()` там просто возвращает `SOCKET_ERROR` — поэтому баг не проявлялся при разработке под Windows). Затрагивает не только бан по IP: любая ситуация, где сервер пишет в уже оборванное клиентом соединение, была тем же риском.

## Архитектурные решения

**Не P2P, а через сервер.** Клиент шлёт только на gateway, тот сам определяет получателей. Это даёт историю, контроль доступа и работу за NAT.

**Активная комната живёт в памяти сессии, не в БД.** Поле `Session::currentRoomId` (atomic). Клик по комнате = переключение в памяти, без запросов к `room_service`. Таблица `room_members` в БД существует, но сейчас не используется — она пригодится позже для ролевой модели и закрытых комнат. Проверка «можно ли писать в эту комнату» сравнивает `roomId` из сообщения с `currentRoomId` сессии.

**Имя автора денормализовано в таблицу messages.** Колонка `sender_name` заполняется в момент отправки, потому что имена живут в БД `auth_service`, а сообщения в БД `message_service` — join между ними невозможен. Побочный эффект: смена ника не переписывает историю, что считается правильным поведением.

**Диапазоны MessageType по слоям.** `0x0000–0x0FFF` — клиент ↔ gateway, `0x1000+` — внутренние вызовы. Один парсер обслуживает оба слоя, но сообщения не смешиваются. На практике для операций, где payload клиента и внутреннего вызова совпадают один в один (Room, Message, Role), gateway форвардит `frame.payload` как есть под тем же `MessageType`, не пересобирая его в отдельный внутренний тип — так поступают все `Handle*Request` в gateway, где вызывается `CallService` с `frame.payload` без предварительного парсинга.

**Роли — глобальные, не по комнатам.** У пользователя есть одна или несколько ролей (`user_roles` в `auth_service`), их права (`roles.permissions`, битовая маска) объединяются через OR в эффективные права пользователя. Роль `admin` (id=1) — суперпользователь: её код всегда пропускает через любую проверку прав независимо от того, что хранится в `roles.permissions` для неё (см. `GetUserPermissions` в `UserRepository.cpp`, возвращает `0xFFFFFFFF`). Роль `guest` (id=2) — то, что получает любой новый пользователь, кроме самого первого (тот становится `admin`, иначе некому было бы выдавать роли). Обе — системные (`is_system=1`): нельзя удалить, `admin` вообще нельзя редактировать, `guest` можно только менять права, не имя.

**Права пользователя кэшируются в сессии на момент логина.** `Session::permissions` — не живая величина: смена ролей пользователя применится только после его следующего логина, gateway не перевычисляет и не рассылает обновление активным сессиям. Список ролей (`Session::roleIds`) кэшируется так же и нужен, чтобы сопоставлять оверрайды каналов с ролями пользователя (см. ниже).

**Права по каналам — оверрайды поверх базовых прав роли.** `channel_role_overrides` в `room_service` (room_id, role_id, allow, deny) хранит явные исключения для роли на конкретном канале — `role_id` ссылается на `roles.id` в другой БД (`auth_service`), FK невозможен, это денормализация того же рода, что `sender_name` в сообщениях. Итоговое право считает gateway (`EffectivePermissionsInRoom` в `gateway/main.cpp`): `(базовые_права & ~объединение_deny) | объединение_allow` по всем ролям пользователя — явный `allow` у любой роли побеждает `deny` у другой, поскольку иерархии ролей (как в Discord) в проекте нет. Для admin (все биты в `Session::permissions`) оверрайды не считаются вообще — иначе оверрайд смог бы отобрать права у суперпользователя. `ViewChannel` фильтрует список комнат, `OpenChannel` — попытку входа и запрос истории (`HandleHistory` — до код-ревью эта проверка отсутствовала вовсе, историю мог прочитать кто угодно), `SendMessages` — отправку текста; `ManageChannel` — глобальное право (не per-канальное), требуется для создания комнаты.

**Модерация по каналам — кик и мьют, оба бессрочны до ручного снятия.** `channel_bans`/`channel_mutes` в `room_service` (`room_id, user_id`, без FK на `users` — та же денормализация, что и везде на стыке БД разных сервисов) хранят состояние per-пользователь, а не per-роль, как оверрайды: мьют нужен именно для конкретного человека независимо от его роли. Кик — это `BanUser` (бессрочный бан от канала) плюс немедленный принудительный выход, если пользователь сейчас онлайн и держит эту комнату открытой (`ForceLeaveRoomIfOnline` в `gateway/main.cpp`, ищет сессию через `SessionManager::GetSessionsForUsers` и присваивает `currentRoomId = 0`, если оно совпадало с комнатой кика — сравнение через `compare_exchange_strong`, а не безусловный `exchange`, иначе можно сбросить пользователю совсем другую открытую комнату). Кикнутый клиент получает отдельный пуш `ChannelKicked`, чтобы не ждать следующей попытки написать. Ровно как с оверрайдами, для admin (сентинел `0xFFFFFFFF`) бан/мьют не проверяются вовсе — иначе роль с `KickMembers`/`ManageChannelModeration` могла бы запереть суперпользователя. `JoinRoom` при бане отвечает статусом `253` (отдельно от `254` — «нет прав»), `TextMessage` при муте молча дропается, как и остальные проверки прав на отправку.

**Бан по IP — на уровне всего сервера, отдельно от ролей и модерации по каналам.** `banned_ips` живёт в `auth_service` (не в gateway — у него нет своей БД, а сам список нужен ещё до логина, то есть это вопрос доступа, а не прав конкретного пользователя). Проверяется в `ClientThread` до TLS-хендшейка: gateway теперь захватывает адрес клиента в `accept()` (`sockaddr_in` + `inet_ntop`, раньше отбрасывался через `accept(listenSocket, nullptr, nullptr)`) и спрашивает auth через internal `IsIpBannedRequest` — если забанен, сокет закрывается немедленно, ни один байт TLS не тратится. По требованию — бан должен обрывать уже активное подключение сразу, а не только блокировать будущие — `Session` хранит `remoteIp` и сырой `rawSocket`; `HandleIpBan` после успешного бана вызывает `DisconnectSessionsForIp`, которая находит все сессии с этим IP через `SessionManager::GetSessionsForIp` и обрывает их `ShutdownSocket` — поток-владелец сессии сам доведёт очистку до конца через свой обычный путь (`ReceiveFrame` вернёт ошибку, дальше как при любом разрыve связи). Гейтится отдельным правом `ManageServerBans` (не `KickMembers`/`ManageChannelModeration` — это разные по масштабу действия).

**Системная комната** — `id = 1`, имя `system`, флаг `is_system = 1`. Создаётся через `INSERT OR IGNORE` при старте `room_service`. В неё падают уведомления о регистрации новых пользователей (отправитель `senderId = 0`, имя `System`).

**Keepalive.** Клиент шлёт `Ping` каждые 15 секунд. Gateway ставит `SO_RCVTIMEO` = 5 секунд и разрывает соединение после 45 секунд тишины (`FrameResult::Timeout` в цикле `ClientThread`). Таймаут посреди кадра не прерывает чтение — иначе кадры разъедутся по границам.

**Sessions через shared_ptr.** Поток-отправитель держит `SessionPtr` живым, даже если владелец сокета отключился в этот момент. `sessionId` генерируется случайно (`mt19937_64`), не счётчиком — чтобы чужую сессию нельзя было угадать перебором.

**TLS обязателен клиент↔gateway, между внутренними сервисами его нет.** `Session::transport` — это `std::shared_ptr<ITransport>` (`TlsTransport` в проде), а вызовы `gateway → auth/room/message` через `ServiceClient::CallService` остаются на голом `PlainTransport`: это чисто loopback-трафик на `127.0.0.1`, шифровать его — отдельная задача (опциональным флагом), не обязательная для первой итерации. Самоподписанный сертификат означает, что доверенного CA нет: клиент проверяет не цепочку, а отпечаток (SHA-256), закреплённый по схеме TOFU (см. инвариант выше).

## Известные ограничения

- **Разное покрытие тестами Windows/Linux.** Сетевой код переведён на слой абстракции `server/common/include/PlatformSocket.h` (`socket_t`, `CloseSocket`, `ShutdownSocket`, `GetLastSocketError`, `IsTimeoutError`, `SetRecvTimeout`, `SocketLibraryGuard`). Собрано и проверено end-to-end на обеих платформах (Windows — нативно, Linux — в WSL2/Ubuntu-24.04, полный сценарий через `dotnet`-клиент на Windows против сервера в WSL). SIGPIPE теперь игнорируется на старте (см. инвариант выше) — раньше это было открытым риском именно потому, что не встречалось на Windows при разработке. Не проверялось: реальный отдельный Linux-хост/сервер без WSL, поведение таймаутов под настоящей нагрузкой.
- **Шифруется только клиент↔gateway.** Внутренние вызовы `gateway → auth/room/message` остаются на голом TCP — это loopback-трафик, не выставленный наружу, но если сервисы когда-нибудь разнесут по разным хостам, это станет критично.
- **Ролевая модель без UI.** Роли, права, оверрайды по каналам (видимость, вход, отправка сообщений), создание каналов, модерация по каналам (кик/мьют) и бан по IP на уровне сервера сделаны и этим закрывают всю серверную часть плана — приватность комнаты через членство конкретных пользователей (`room_members`) сознательно не нужна: обычный пользователь ничего не настраивает и не создаёт сам, всё делает admin через роли и оверрайды, а этого для приватности достаточно (сними `ViewChannel` у всех ролей кроме нужной — комната и станет приватной). `room_members` остаётся в схеме неиспользуемым — понадобится только если появятся пользовательские приватные чаты/DM, что не входит в текущий сценарий. Не сделано: UI для управления ролями/правами/модерацией/банами (пока только `test_client`/`FreeCord.ConsoleTest`). Отдельно: с появлением проверки `ManageChannel` на создание комнаты обычный `guest` больше не может создавать комнаты по умолчанию — раньше мог любой залогиненный.
- **UI минимальный.** Нет списка участников, аватаров, группировки сообщений.
- **Кодировка консоли.** Консольные клиенты на C++ шлют русский текст в CP866, а C# ждёт UTF-8 — кириллица между ними бьётся. В GUI-клиенте всё корректно. Лечится вызовом `SetConsoleOutputCP(CP_UTF8)` / `SetConsoleCP(CP_UTF8)`, но это не сделано, так как консольные клиенты отладочные.

## Планы, в порядке приоритета

1. ~~**Портирование сервера на Linux**~~ — слой абстракции `server/common/include/PlatformSocket.h`, полный сценарий проверен на Ubuntu-24.04 под WSL2.
2. ~~**JSON-конфигурация**~~ — `server/config.json`, `server/common/include/Config.h` + `LoadConfig`.
3. ~~**Система миграций БД**~~ — `PRAGMA user_version` + `MigrationRunner` (`server/common/include/MigrationRunner.h`), SQL-миграции и запросы вынесены в `server/db/<сервис>/`, схема меняется без потери данных и без удаления `.db` вручную.
4. ~~**Серверная часть вынесена в отдельную папку**~~ — `server/` рядом с `client/`, чтобы структура репозитория не выглядела так, будто весь проект — это `client/`.
5. ~~**TLS клиент↔gateway**~~ — OpenSSL, самоподписанный сертификат (`server/common/include/TlsContext.h`), TOFU-pinning по отпечатку на клиенте (`client/FreeCord.Protocol/TrustedServerStore.cs`). TLS между внутренними сервисами опциональным флагом — не сделано, отложено (loopback-трафик, не приоритет).
6. **Установщик для сервера** — systemd-юниты, автозапуск, скрипт развёртывания.
7. **Ролевая модель** — серверная часть готова. Сделано: таблицы `roles`/`user_roles` в `auth_service`, системные роли `admin`/`guest` с бутстрапом (первый пользователь — admin), CRUD ролей и назначение пользователям через протокол (`RoleMessages.h`), проверка `ManageRoles`/`ManageChannel` на gateway, права пользователя приходят клиенту после логина (`MyPermissions`, включая список ролей), права по каналам через оверрайды (`channel_role_overrides` в `room_service`, `server/db/room/migrations/002_channel_overrides.sql`) — видимость, вход, отправка сообщений, в том числе используются как единственный механизм приватности комнат (сознательное решение: обычный пользователь ничего не настраивает сам, `room_members` для этого не нужен); модерация по каналам — кик (бан + принудительный выход онлайн-пользователя) и мьют, оба бессрочны до ручного снятия (`channel_bans`/`channel_mutes`, `server/db/room/migrations/003_channel_moderation.sql`, права `KickMembers`/`ManageChannelModeration`); бан по IP на уровне всего сервера — тоже с немедленным разрывом активного подключения (`banned_ips` в `auth_service`, `server/db/auth/migrations/003_ip_bans.sql`, право `ManageServerBans`). Осталось только отражение в UI.
8. **Голос и видео** — UDP, SFU-релей на сервере, Opus и H.264 через FFmpeg. Планировался `MediaPacketHeader` с `sessionId`, `senderId`, фрагментацией и `frameId`; сервер форвардит пакеты как есть, без декодирования.

## Стиль работы

Проект строится пошагово: одна законченная вещь за раз, с проверкой перед переходом к следующей. Это осознанно — так ошибка локализуется в свежем коде, а не ищется сразу в нескольких новых компонентах. Не стоит браться за несколько пунктов из планов одновременно.

При изменениях, затрагивающих обе стороны протокола, проверяй совместимость запуском двух клиентов одновременно — GUI и консольного.
