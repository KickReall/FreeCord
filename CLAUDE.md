# FreeCord

Self-hosted мессенджер (аналог Discord). Сервер — микросервисы на C++, клиент — C# / Avalonia. Собственный бинарный протокол поверх TCP. Никаких внешних зависимостей и облаков: всё разворачивается на своём хосте.

Общение с пользователем — на русском языке.

---

## Структура

```
common/                  Общий код сервера (статическая библиотека)
  include/
    ProtocolTypes.h      ControlHeader + enum MessageType
    Serialization.h      WriteString/ReadString, WriteScalar/ReadScalar
    TcpFramer.h/.cpp     Кадрирование поверх TCP
    ServiceClient.h      CallService — вызов внутреннего сервиса
    WinsockGuard.h       RAII над WSAStartup/WSACleanup
    *Messages.h          Структуры payload по доменам
services/
  gateway/               Порт 6000. Точка входа, сессии, fanout. Своей БД нет
  auth/                  Порт 6001. Регистрация/логин, PBKDF2. freecord_auth.db
  room/                  Порт 6002. Комнаты. freecord_rooms.db
  message/               Порт 6003. Сообщения и история. freecord_messages.db
client/
  FreeCord.Protocol/     Библиотека протокола на C#, без UI
  FreeCord.Desktop/      Avalonia + CommunityToolkit.Mvvm
  FreeCord.ConsoleTest/  Консольный клиент для отладки
tools/test_client/       Консольный клиент на C++
```

## Команды

Сервер, сборка под Windows (из корня проекта):
```powershell
mkdir build-windows; cd build-windows
cmake .. -DCMAKE_TOOLCHAIN_FILE=C:/vcpkg/scripts/buildsystems/vcpkg.cmake
cmake --build .
```

Сборка под Linux делается отдельно, в WSL/Linux-окружении, в свою папку `build-linux` — см. раздел «Портирование на Linux» ниже.

Запуск — четыре процесса, каждый в своём окне, из папки `build-windows`:
```
.\services\auth\Debug\auth_service.exe
.\services\room\Debug\room_service.exe
.\services\message\Debug\message_service.exe
.\services\gateway\Debug\gateway_service.exe
```

Клиент:
```powershell
cd client\FreeCord.Desktop
dotnet run
```

Зависимости через vcpkg: `sqlite3`, `sqlitecpp`, `openssl`.

## Критические инварианты

**Сериализация C++ и C# должна совпадать байт в байт.** При изменении любой структуры в `common/include/*Messages.h` обязательно нужна зеркальная правка в `client/FreeCord.Protocol/Payloads.cs`, и наоборот. Порядок полей, их типы и размеры должны совпадать точно. Формат: строки — `uint16` длина в байтах + UTF-8 без null-терминатора; числа — little-endian (совпадает у `#pragma pack(1)` в C++ и `BinaryWriter` в .NET). При добавлении нового `MessageType` его нужно продублировать в `client/FreeCord.Protocol/MessageType.cs` с тем же числовым значением.

**Миграций БД нет.** Таблицы создаются через `CREATE TABLE IF NOT EXISTS` в конструкторах репозиториев. Если меняется схема — существующий `.db` файл не обновится, его надо удалить вручную из `build-windows/` (или `build-linux/`). Всегда предупреждай об этом при изменении схемы.

**Чтение из сокета всегда в цикле.** TCP отдаёт поток байт, а не сообщения; один `recv` может вернуть меньше запрошенного. Это уже реализовано в `RecvAll`/`SendAll` в `TcpFramer.cpp` и в `ReadExactlyAsync` на стороне C#. Не заменяй на одиночные вызовы.

**Порядок функций в gateway/main.cpp.** `SendToSession` → `BroadcastToRoom` / `BroadcastToAll` → `Handle*` → `ClientThread` → `main`. C++ читает файл сверху вниз, вызов выше определения не компилируется.

**Запись в чужой сокет только через `SendToSession`.** Fanout идёт из потока одного клиента в сокеты других. Каждая сессия имеет свой `sendMutex`; прямой `SendFrame` в чужой сокет приведёт к перемешиванию кадров.

## Архитектурные решения

**Не P2P, а через сервер.** Клиент шлёт только на gateway, тот сам определяет получателей. Это даёт историю, контроль доступа и работу за NAT.

**Активная комната живёт в памяти сессии, не в БД.** Поле `Session::currentRoomId` (atomic). Клик по комнате = переключение в памяти, без запросов к `room_service`. Таблица `room_members` в БД существует, но сейчас не используется — она пригодится позже для ролевой модели и закрытых комнат. Проверка «можно ли писать в эту комнату» сравнивает `roomId` из сообщения с `currentRoomId` сессии.

**Имя автора денормализовано в таблицу messages.** Колонка `sender_name` заполняется в момент отправки, потому что имена живут в БД `auth_service`, а сообщения в БД `message_service` — join между ними невозможен. Побочный эффект: смена ника не переписывает историю, что считается правильным поведением.

**Диапазоны MessageType по слоям.** `0x0000–0x0FFF` — клиент ↔ gateway, `0x1000+` — внутренние вызовы. Один парсер обслуживает оба слоя, но сообщения не смешиваются.

**Системная комната** — `id = 1`, имя `system`, флаг `is_system = 1`. Создаётся через `INSERT OR IGNORE` при старте `room_service`. В неё падают уведомления о регистрации новых пользователей (отправитель `senderId = 0`, имя `System`).

**Keepalive.** Клиент шлёт `Ping` каждые 15 секунд. Gateway ставит `SO_RCVTIMEO` = 5 секунд и разрывает соединение после 45 секунд тишины (`FrameResult::Timeout` в цикле `ClientThread`). Таймаут посреди кадра не прерывает чтение — иначе кадры разъедутся по границам.

**Sessions через shared_ptr.** Поток-отправитель держит `SessionPtr` живым, даже если владелец сокета отключился в этот момент. `sessionId` генерируется случайно (`mt19937_64`), не счётчиком — чтобы чужую сессию нельзя было угадать перебором.

## Известные ограничения

- **Разное покрытие тестами Windows/Linux.** Сетевой код переведён на слой абстракции `common/include/PlatformSocket.h` (`socket_t`, `CloseSocket`, `GetLastSocketError`, `IsTimeoutError`, `SetRecvTimeout`, `SocketLibraryGuard`). Собрано и проверено end-to-end на обеих платформах (Windows — нативно, Linux — в WSL2/Ubuntu-24.04, полный сценарий через `dotnet`-клиент на Windows против сервера в WSL). Не проверялось: реальный отдельный Linux-хост/сервер без WSL, поведение таймаутов/SIGPIPE под настоящей нагрузкой.
- **Нет шифрования.** Пароли ходят открытым текстом. На localhost неважно, при выставлении в интернет — критично.
- **Порты и пути захардкожены** в константах `main.cpp` каждого сервиса.
- **Нет ролевой модели.** Все комнаты доступны всем залогиненным.
- **UI минимальный.** Нет списка участников, аватаров, группировки сообщений.
- **Кодировка консоли.** Консольные клиенты на C++ шлют русский текст в CP866, а C# ждёт UTF-8 — кириллица между ними бьётся. В GUI-клиенте всё корректно. Лечится вызовом `SetConsoleOutputCP(CP_UTF8)` / `SetConsoleCP(CP_UTF8)`, но это не сделано, так как консольные клиенты отладочные.

## Планы, в порядке приоритета

1. ~~**Портирование сервера на Linux**~~ — сделано в ветке `dev`. Слой абстракции `common/include/PlatformSocket.h`, сборка и полный сценарий (регистрация/логин/комнаты/сообщения через `dotnet`-клиент на Windows) проверены на Ubuntu-24.04 под WSL2. Ветка ещё не влита в `main`.
2. **JSON-конфигурация** — порты, пути к БД, адреса хостов вместо констант.
3. **Система миграций БД** — таблица `schema_version` и последовательное применение SQL-файлов, чтобы менять схему без потери данных.
4. **TLS** — обязательный для клиент↔gateway, опциональный флагом для межсервисных соединений. Планировался через OpenSSL с самоподписанным сертификатом и проверкой по отпечатку (pinning). Классы `TlsContext` и `TlsSocket` были спроектированы, но в репозиторий не попали.
5. **Установщик для сервера** — systemd-юниты, автозапуск, скрипт развёртывания.
6. **Ролевая модель** — приватные комнаты, права. Здесь пригодится `room_members`.
7. **Голос и видео** — UDP, SFU-релей на сервере, Opus и H.264 через FFmpeg. Планировался `MediaPacketHeader` с `sessionId`, `senderId`, фрагментацией и `frameId`; сервер форвардит пакеты как есть, без декодирования.

## Стиль работы

Проект строится пошагово: одна законченная вещь за раз, с проверкой перед переходом к следующей. Это осознанно — так ошибка локализуется в свежем коде, а не ищется сразу в нескольких новых компонентах. Не стоит браться за несколько пунктов из планов одновременно.

При изменениях, затрагивающих обе стороны протокола, проверяй совместимость запуском двух клиентов одновременно — GUI и консольного.
